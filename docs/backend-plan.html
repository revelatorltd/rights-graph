Where we stand

We don't need more broad documentation. The FRD, the data-model doc and the prototype already define what the backend does. What is missing is a short list of decisions only the business and our partners can make, three precise specs, and real data. With those in hand, we build one thin working slice end to end instead of planning further.

The plan

Four phases to the first AI deal

Dates are proposals, set against the two fixed points: the gate on 30 November and an AI deal reading the graph by 18 January.

Phase 026 Oct – 6 NovDecide

Settle the decisions and freeze the tests

  • Agree who builds and on what stack; record it and the policy calls as short architecture decision records.
  • Inventory what existing code can be ported versus what is still only a spec.
  • Write ingestion spec #1 from a real Revelator Pro export.
  • Freeze a golden test set: the worked example plus a few hundred real records with hand-checked answers.
Done when the stack is chosen, every decision above has an owner and a date, and the golden set runs in CI.
Phase 19 – 27 NovBefore the gate

One thin slice, end to end, on real data

  • The Postgres schema in a real database, with migrations.
  • The write path: command, event log and outbox in one transaction.
  • Resolver v1 for performance and mechanical rights, writing pinned graph versions.
  • The splits and effective-clearance read APIs.
  • Revelator Pro catalogue ingestion.
  • The coverage metric on Revelator-held catalogue, so the gate has a defensible number.
  • The prototype pointed at the real API: its screens become the first client and the visual check.
Done when a real catalogue loads, the splits API returns the golden set's answers, and the coverage number is reported per lane.
Phase 230 Nov – 18 DecResolve and contribute

Conflicts, contributors and society data

  • Conflict detection (overclaims, gaps, missing links) and the operations queue.
  • Contributor tenants with row-level security and encrypted private terms.
  • CWR and acknowledgement ingestion; matching with reversible merges.
  • Coverage computed for every data source.
Done when a peer contributor can upload into its own tenant, see its match results, and no other tenant can read its private terms.
Phase 34 – 15 JanClear and serve

Clearance, proof and partners

  • Clearance grants and attestations, signed with real keys.
  • The Proof Log as its own service: hash chain, Merkle batches, external timestamps.
  • Partner keys, scopes and webhooks; receipts that verify without an account.
  • Notifications and escalation for the approval inbox.
Done when an AI partner asks the clearance API for a catalogue, gets a per-track answer with a receipt, and an auditor verifies the receipt offline.
Working together

How the team stays in sync

  • One repository is the source of truth. The prototype, docs, schema and tests live in revelatorltd/rights-graph; the backend joins it or sits beside it, sharing the schema and the tests.
  • Work on branches, merge by pull request. Every push to main redeploys the live prototype, so reviewers always see the current state.
  • The tests run on every pull request. Type checks, the design system's page checks, the API checks and the database checks; the golden set joins them in Phase 0.
  • Decisions are written down where the code is. Each policy call becomes a short decision record next to the rule it changes, so the reason travels with the code.
  • The design system is versioned too. The prototype builds against a packaged copy; the design-system repository should be committed and pushed so its changes are reviewable.

Three things we need from the team

The nine decisions above. The prototype's defaults hold until each is signed off.

One real data sample

A Revelator catalogue export with splits and agreements, so ingestion spec #1 and the golden set are written against real records.

Risks

What could slip

  • The stack decision runs late. Mitigation: Phase 0 work (specs, golden set, decision records) is stack-neutral and starts now.
  • Real data arrives late. Mitigation: run the coverage metric on Revelator-held catalogue first to prove the method.
  • Scale surprises the schema. Mitigation: load a full catalogue in Phase 1 and partition the largest tables before Phase 2.
  • Policy calls change late. Mitigation: each is one rule in the resolver, versioned and replayable, so a change shows exactly which answers move before it ships.
